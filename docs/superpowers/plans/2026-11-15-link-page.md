# Link Page (no-app visitors) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Tasks run in PARALLEL worktrees off the skeleton commit; each task owns only its listed files. Steps use checkbox (`- [ ]`) syntax.

**Goal:** A no-login web link page where someone who got a paper boat link can, in ~30s, make one free wish, then claim or push the boat (to exactly one person), leave a contact, and see "your wish set sail".

**Architecture:** New Expo-router route `src/app/l/[hopId].tsx` (web-first, also works native) runs a 6-step wizard over a new Convex module `convex/link.ts`. Share links go through a Convex HTTP route `/og/w/:hopId` that serves OG meta for WeChat/iMessage/IG and redirects to the hosted web app. Notifications use a pluggable notifier (Twilio Messaging when configured, else log). Funnel metrics come from a `linkEvents` table.

**Tech Stack:** Expo SDK 58 + expo-router (web export), Convex (+ file storage, scheduler, http actions), OpenAI via existing `respond` helper, Twilio Verify via `convex/sms.ts`.

**Spec:** `docs/superpowers/specs/2026-11-15-link-page-prd.md`

## Global Constraints
- No login, no app download needed for any core step; download prompts only on done screen, ending page, and after claim confirmation, never blocking.
- One link = one boat = one recipient. Push to exactly **1** person per link; the vouch is written about the **next** person.
- One free wish per visitor, deduped by contact (normalized phone E.164 or lowercase email). Later wishes: 5 boats pushed = 1 coin (`BOATS_PER_COIN`, existing `users.boatProgress`).
- Boat lifetime 48h (existing `expiresAt`). Contact (phone or email) is required before the done screen.
- AI polish returns within 3s or falls back to the user's text. Share copy describes only the wish and vouch — never "forward to unlock".
- Copy is in English for UI (app convention); keep the PRD's wording meaning. Reuse `src/theme/tokens.ts` (`lv`).
- Every public Convex function: `requireDeviceId`, `clampText`/`LIMITS`, `aiAllowed` for AI, bounded reads; never return another visitor's contact.
- No "Lovable" and no Claude attribution in code, comments, commits, or PR bodies.

## Builder decisions (PRD silent)
- Visitor identity = existing device id (`src/lib/device.ts`, works on web) → `users.ensure`. The first device to open a link binds the hop (`hops.holderUserId`); a different device later sees the "forwarded" state.
- The free wish sails to the **person who sent you the link** (the parent hop's holder, or the wish creator at depth 1) as its first hop, with the visitor's wish text; mode `"serious"`. It is created only when the visitor finishes (`link.finish`).
- Vouch about the next person is stored on the child hop as `hops.introVouch` and shown at the top of that person's first screen.
- Real-wish claim requires phone verification via `sms.sendCode/checkCode` (demo numbers + Twilio). Wisher confirmation (`link.confirmClaim`) exchanges both phones by SMS.

## Review Focus
- Visitor opens the same link twice (refresh) → resumes at their step / "already handled" state, never double-creates a free wish or a second child hop.
- Visitor enters an email in a different case or a phone with spaces → dedupe still finds the same visitor (normalized key).
- Push target name equals the visitor's own name or any upstream holder (case/space-insensitive) → rejected with "Pick someone else — this boat already passed through them".
- OpenAI slow/unavailable → polish/vouch/prophecy fall back to templates within 3s; page never spins forever.
- Link opened after 48h or after someone else claimed → correct special-case screen with the free-wish entry still available.
